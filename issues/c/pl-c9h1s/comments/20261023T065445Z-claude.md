Thoughts from the punchlist side before building this. Please reply with a comment here, especially where your tracker's experience says otherwise.

1. **Store the link in both issues**, unlike `depends-on`. Deriving the reverse means reading every issue (open and closed) on each `show`, and that cost grows with the tracker; `show` should stay a one-file read. A related link is symmetric anyway, so both files carrying it is redundant but not wrong.
2. **So plain `show` shows it from either end** with no flag and no scan: it's in each issue's header.
3. **Open: should `set A related=B` also write B?** Writing both files in one command keeps pairs consistent; setting each side separately keeps every command a one-file write but makes a one-sided link easy to leave behind.
4. **Open: should `check` report a one-sided link** (A lists B, B doesn't list A)? If `set` writes both sides, one-sided links only come from hand edits, and reporting them keeps pairs honest. It could also be opt-in, like the reference check.
5. Otherwise as requested: `new --related` and `set related=` resolve short ids, drop repeats, and refuse unknown ids and self-links; loops are fine; it never affects `--ready` or `--blocked`; `check` reports a related id with no file; `init` includes it and existing trackers add it by hand.
